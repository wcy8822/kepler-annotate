# V1.5 AI 前端评审迭代计划

目标是在现有批注编辑器内完成“识别类别 → 整理建议 → 用户确认 → 结构化开发任务”。原话、原编号和图片证据始终保留；用户可以编辑建议、拒绝建议或只保存原话。

源码与进度统一保存在本仓库。代码、协议、测试与文档可以通过开发分支和 PR 持续推进；扩展运行、真实网页截图和 Native Messaging 实机连接属于单独的验收环节。

## 基线与范围

本轮基于 `ba7a7a99d45961649e4bc1183612ac1b2b82acc7`。`manifest.json` 与 `package.json` 均为 v1.4.0；版本在发布验收时统一更新。

| 能力 | 当前依据 | V1.5 工作 |
| --- | --- | --- |
| 点选、圈选、截图、批次管理 | `kp-annotate.js`、`service-worker.js` | 在原编辑器增加可选建议区 |
| 分类 | `视觉`、`文案`、`交互`、`产品逻辑`、`反馈/建议` | 输出建议类别和理由，允许无法判断；用户确认后采用 |
| 原始数据与 ZIP | `kp-annotate-store.js`，原始批次 schemaVersion 1 | 不改写原话；确认规格作为附加语义，导出时与证据一起保留 |
| 本地交接 | `native-host.py`、`project_store.py`、CLI、Skill | 复用项目快照和条目版本，增加评审契约识别与来源校验 |
| AI 结果和用户状态 | 精确 item revision 回写，用户单独验收 | 保持独立；AI 建议被采纳不代表问题已修复 |
| 即时 AI | 尚无内置调用或后台常驻 AI | 分步加入只读建议通道，调用不阻塞保存、截图和同步 |

## 最小产品体验

1. 用户选中元素或区域后，原批注编辑器立即可写、可保存。圈选本身不证明存在问题；无足够信息时显示“需要补充预期”，不制造错误结论。
2. 本地轻量规则根据用户反馈和有限元素语义给出候选类别。候选不覆盖已选类别；规则与模型来源明确标识。
3. 项目开启智能建议后，在输入停顿时请求一次建议。界面展示“观察到什么、可能影响、建议怎么改、如何验收、还需确认什么”。将可见事实、推测和建议分开，不凭一张截图断言交互结果或业务规则。
4. 建议区提供“采用建议”“编辑后采用”“仅保留原话”“拒绝”。采纳类别是独立明确动作；原文输入区与建议正文分开。
5. 用户确认后冻结当次建议与证据，生成附着于原条目的开发规格。再次改原话、类别或证据时，旧规格必须重新确认；拒绝和撤回也保留来源关系，不重新编号。
6. 继续通过原来的项目同步、CLI、Skill 消费任务。原始意见与采纳后的规格同时可读；结果仍按 item revision 回写，由用户最终验收。

响应目标属于待测指标：规则建议不应有可感知等待；模型请求超过约 2 秒显示进度，约 15 秒给出可继续等待或取消的操作。超时、模型不可用和无图像能力时，原批注功能继续工作。真实响应时间必须按模型与设备记录，不能用目标代替测试结果。

## 接入方式与边界

| 接入方式 | 隐私与权限 | 成本与体验 | 迭代取舍 |
| --- | --- | --- | --- |
| 本地规则 | 仅处理本次用户主动选择的上下文，无模型传输 | 无模型费用、响应快，理解能力有限 | 先做基础分类与空信息提示 |
| 本地 Agent 的只读建议适配器 | Agent 在本机运行不代表模型离线；需明示其真实模型目的地。建议阶段不授予仓库写入或命令执行工具 | 可复用配置，冷启动与队列延迟需测；原 `send` 只排队，不能充当即时返回通道 | 优先复用 Native Messaging 增加独立请求/状态接口 |
| 用户自配模型 | 凭据留在本地主机配置，内容脚本不可接触；用户选择端点、模型和允许发送的数据 | 由用户承担提供方费用；可设请求次数、超时和用量上限，用量未知时不显示精确金额 | 在来源绑定和发送授权后接入一个适配器，逐步扩展 |
| 本地推理服务 | 仅当服务和模型均本地且无外发时才称离线；仅允许用户配置的回环端点 | 无按次云调用费用但有硬件与运行成本，图像能力和速度不一 | 使用相同建议接口，实测能力后启用 |
| 扩展直接云 API / 托管代理 | 新增网络目的地、权限、凭据或服务端数据处理边界 | 安装更少，但有服务成本与额外运维 | 不纳入首个 MVP；以后单独设计授权与数据保留策略 |

首次开启按项目授权文字与最小 DOM 线索；截图传输采用独立预览与确认，显示发送目的地、裁剪范围和脱敏结果。授权绑定具体请求与实际发送内容 hash；换端点、换图片或内容变化后失效。页面内文本不能替用户点击授权。默认不收集输入框值、密码、完整 DOM、cookie 或整页网络记录。

选择器和 URL 也可能含个人信息。后续上下文提取必须先过滤 query/hash、任意 data 属性和敏感值，再形成发送预览。裁剪不能只按比例估算；缩放、DPR、滚动、iframe 与页面变化都需要真实浏览器验证。

## 分步实施

| 阶段 | 交付 | 验收边界 |
| --- | --- | --- |
| A：任务契约保护 | v2 结构与证据 hash 校验、显式消费确认、精确版本保护、防止评审语义被删除、结果回写限制 | 本轮实现；来源绑定未完成前，含评审的任务只能审阅和登记待确认 |
| B：批准来源绑定 | 定义 source/context 的规范化与 H0→H1 转换；核验用户确认来源、类别采纳和新增证据；撤回与重新确认版本化 | 先做纯函数与跨语言黄金用例，验证通过后才开放已批准任务执行 |
| C：编辑器建议区 | C1 已增加原编辑器本地类别候选与显式采用/忽略，不写入评审批准；下一步是原话并列的模型建议编辑/拒绝与草稿过期响应处理 | C1 单元与合成 UI 检查，真实 Chrome/用户手势仍待实机验证 |
| D：只读模型适配器 | 新增 Native review 请求/状态/取消接口、单个适配器、超时和能力检测 | 复用原主机；不占用现有串行存储队列；不自动启动开发 Agent |
| E：证据与发送授权 | 安全裁剪、预览、按请求授权、实际发送内容 hash、最小 DOM 上下文 | 必须有真实浏览器与实际目的地验证；无授权不发送 |
| F：端到端与发布 | 保存 → 同步 → CLI/Skill → 回写 → 用户验收；断连恢复和原位更新 | 真实扩展/主机联调后再标记支持平台、统一升至 v1.5.0 |

每轮先核对最新 main、已有 PR 和检查结果；继续合适的开发分支，完成一个可独立验证的改动，更新本页日志。代码变更在 Draft PR 中审查，不以无人值守任务自动合并或发布。某个平台验收被阻塞时，继续其他可独立完成的任务，准确记录阻塞。

### 下一轮可直接交给开发 Agent 的任务

在阶段 A 代码基础上实施阶段 B，不提前接入模型：

- 定义浏览器与 Python 一致的规范化 source/context 数据以及 hash 规则，明确排除运行中候选、计费、拒绝记录和时间戳噪声。
- 将用户确认时的原始依据 H0、允许的类别采纳/证据追加转换、最终适用版本 H1 分开验证。普通编辑不等于合法转换。
- 校验 `approvedSnapshot`、`approvedReview`、条目源内容、实际图片字节一致；决定 ID、撤回和重新确认不能复用旧版本结果。
- 在已验证分支中解除合适状态的执行限制，其他状态继续受保护；旧 v1 黄金 hash 不变，混合批次中普通条目不受影响。
- 保持 Native 直送 v2 禁用，直到该通道也具有明确消费契约。新增权限、远端调用和凭据存储应留在对应阶段。
- 提交前运行 `npm test` 与 `npm run check:public`，补篡改、竞态、旧版本重放和失败恢复用例，在 PR 中区分已测试与待实机验证。

### B1 的验证记录（2026-11-01）

本轮只加入纯函数 `review-source.js` / `review_source.py`、共用合成黄金向量和双端测试，不修改现有浏览器入口、项目快照、ZIP、CLI、Skill 或任务执行逻辑。隔离环境执行 `node --test tests/review-source.test.cjs`（3/3）与 `python3 -B tests/review-source.test.py -v`（3/3），均退出码 0。GitHub 上的完整 `npm test` 和 `check:public` 以本轮提交对应 CI 为准。

核心不变量：原编号、原话、五类分类、实际/预期/复现文本、原截图及参考图引用与逐图片 SHA-256 参与来源摘要；状态、时间戳、候选建议不参与。路径按 UTF-8 字节排序并用固定 JSON 字段顺序；使用 SHA-256 摘要，浏览器 Web Crypto 与 Python hashlib 的三个冻结向量完全一致（含非 ASCII 文件名、图片和空图片列表）。非法图片集合、重复引用、无效 Unicode 或不安全路径拒绝计算。
